## Task 69: Create Variance Approval Workflow

**Complexity:** High | **Time Estimate:** 30 min

### Objective
Implement multi-level approval workflow for stock take variances that exceed defined thresholds.

### Instructions

#### 1. Define Approval Thresholds
- Create configuration model or settings for thresholds
- Define levels:
  - LEVEL_1: Variance up to $500 or 5% - Supervisor approval
  - LEVEL_2: Variance $500-$2000 or 5-10% - Manager approval  
  - LEVEL_3: Variance >$2000 or >10% - Director approval
- Allow per-warehouse threshold customization

#### 2. Add Approval Fields to Models
- Add to StockTake: `approval_status` (NOT_REQUIRED, PENDING, APPROVED, REJECTED)
- Add to StockTakeItem: `requires_approval`, `approval_status`
- Add `approval_requested_at`, `approval_responded_at` timestamps
- Add `approval_notes` TextField for approver comments

#### 3. Create Approval Determination Logic
- Method: `determine_approval_requirements(stock_take)`
- Analyze all variances after counting complete
- Classify items by approval level needed
- Set `requires_approval` flag on items exceeding thresholds
- Update stock take overall approval status

#### 4. Implement Request Approval Method
- Method: `request_approval(stock_take_id, user)`
- Transition stock take to REVIEW status
- Identify required approvers based on variance levels
- Create approval tasks/notifications
- Send email/notification to approvers with summary

#### 5. Create Approve/Reject Methods
- Method: `approve_variance(stock_take_item_id, approver, notes=None)`
- Verify approver has required permission level
- Update item approval_status to APPROVED
- Record approver and timestamp
- Check if all items approved, allow completion

- Method: `reject_variance(stock_take_item_id, approver, reason)`
- Update item approval_status to REJECTED
- Add rejection reason to notes
- Require re-count or escalation

#### 6. Add Bulk Approval Support
- Method: `approve_all_items(stock_take_id, approver, notes=None)`
- Approve all pending items user has authority for
- Skip items requiring higher authority
- Return summary of approved/skipped items

### Validation Checklist
- [ ] Thresholds properly configured
- [ ] Approval requirements determined correctly
- [ ] Notifications sent to correct approvers
- [ ] Permission levels enforced
- [ ] Rejected items handled appropriately
- [ ] Bulk approval efficient and safe

## Task 71: Add Blind Count Support

**Complexity:** Medium | **Time Estimate:** 20 min

### Objective
Implement option to hide expected quantities from counters during counting to improve accuracy.

### Instructions

#### 1. Add Blind Count Option
- Add `is_blind_count` BooleanField to StockTake model
- Default to False
- Set at stock take creation or before starting

#### 2. Modify API/UI for Blind Counts
- When retrieving items for counting, check `is_blind_count`
- If True, exclude `expected_quantity` from response
- Show only: product, location, count input field
- Do NOT show system quantity or previous counts

#### 3. Create Blind Count Serializer
- Separate serializer: `BlindStockTakeItemSerializer`
- Include: id, product (name, SKU), location, counted_quantity input
- Exclude: expected_quantity, variance fields
- Use when `is_blind_count = True`

#### 4. Reveal Expected After Count
- Once counter submits counted_quantity, reveal expected
- Show variance immediately after submission
- Allow counter to review and confirm or re-count
- Ensure counter can't see expected before counting

#### 5. Add Double Blind Count Option
- Add `requires_verification` BooleanField
- If True, require second counter to verify
- Second counter also doesn't see first count or expected
- Compare both counts, if match, accept; if differ, require supervisor review

#### 6. Track Blind Count Accuracy
- Compare blind count accuracy vs regular counts
- Generate report: blind counts reduce discrepancies by X%
- Use data to decide when to require blind counts
- Track counter reliability in blind vs non-blind

### Validation Checklist
- [ ] Blind count option configurable
- [ ] Expected quantities properly hidden
- [ ] Reveal logic works after count
- [ ] Double blind verification functional
- [ ] Accuracy tracking implemented
- [ ] UI/API properly handle both modes

## Task 72: Create Cycle Count Scheduling

**Complexity:** High | **Time Estimate:** 30 min

### Objective
Implement automatic scheduling system for rotating partial stock counts (cycle counting).

### Instructions

#### 1. Create ABC Classification System
- Add `abc_classification` CharField to Product model
- Choices: A (high value/velocity), B (medium), C (low)
- Calculate based on: annual value, turnover rate
- Method: `classify_products_abc(warehouse)` - classify all products

#### 2. Define Cycle Count Schedules
- Create `CycleCountSchedule` model
- Fields: warehouse, classification (A/B/C), frequency (days)
- Example: A items - every 30 days, B - every 90 days, C - every 180 days
- Allow custom schedules per warehouse

#### 3. Add Last Counted Tracking
- Add `last_counted_date` DateField to StockLevel or Product
- Update after each stock take that includes product
- Use to determine which products are due

#### 4. Implement Due Products Query
- Method: `get_products_due_for_count(warehouse, classification=None)`
- Query products where:
  - `last_counted_date` is null OR
  - Days since `last_counted_date` >= schedule frequency
- Order by: most overdue first
- Limit to manageable count size (e.g., 50-100 items)

#### 5. Create Automatic Stock Take Generation
- Celery periodic task: `create_cycle_counts_task`
- Run daily or weekly
- For each warehouse:
  - Check schedule
  - Get due products
  - Create stock take with scope=CYCLE
  - Assign to warehouse team
- Send notification about new cycle count

#### 6. Add Cycle Count Dashboard
- Show upcoming and overdue cycle counts
- Display: products due by classification
- Visualize: count frequency compliance
- Allow manual trigger of cycle count for specific products

### Validation Checklist
- [ ] ABC classification accurate
- [ ] Schedule configuration flexible
- [ ] Due products query correct
- [ ] Automatic generation reliable
- [ ] Periodic task runs on schedule
- [ ] Dashboard shows actionable data

### Cycle Count Schedule Example

For warehouse with 1000 products:
- 200 Class A products → ~7 items/day (30-day cycle)
- 300 Class B products → ~3 items/day (90-day cycle)  
- 500 Class C products → ~3 items/day (180-day cycle)
- **Total: ~13 items/day** - manageable continuous counting
